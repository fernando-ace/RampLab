# Goal 28: Live Operational Control

## Purpose and authority

Goal 28 adds an operator-controlled, deterministic run to the Goal 27 KAUO simulation workflow. The C++ `Simulation` remains authoritative for simulation time, aircraft and vehicle state, routes, resource assignments, closures, events, and metrics. The dashboard sends typed commands to the native CLI; it does not edit snapshots or calculate operational outcomes. Unreal can mirror the live state stream for presentation but does not advance the simulation in this mode.

The KAUO schedule, aircraft identities, equipment inventory, service durations, taxi graph, stands, and road closure are simulation inputs and assumptions documented in [Goal 27](goal27-kauo-operational-digital-twin.md). The example is not a record of actual KAUO activity or a validated airport digital twin.

## Operator workflow

Start the dashboard server from PowerShell in the repository root after building the native CLI:

```powershell
cmake -S . -B build-goal28 -G "Visual Studio 18 2026" -A x64 -DBUILD_TESTING=ON
cmake --build build-goal28 --config Release --parallel 4
python -m tools.ops_dashboard.server --host 127.0.0.1 --port 8768 `
  --live-cli build-goal28/Release/airside_cli.exe `
  --live-root results/goal28/live-session
```

Open `http://127.0.0.1:8768`, choose **Live operator**, and start the fixed `airport_kauo`, seed 42 session. The view exposes aircraft, service vehicles and tasks, road state, runway queue/owner, current event history, and session time. Operators can pause/resume, reset, choose 1x/2x/5x/max presentation pacing, advance a native event, apply an edge closure/opening or vehicle outage, finish the run, replay the recorded inputs, or launch the Unreal mirror. Pacing only controls wall-clock delay between native event advances; it does not change event timestamps or the seed.

The HTTP control interface is under `/api/session`: `GET` returns current state, `POST` routes handle `start`, `pause`, `resume`, `reset`, `speed`, `advance`, `intervention`, `finish`, `replay`, and `unreal`; `/api/session/artifacts` serves the finished native run and Goal 19 outputs. The CLI's `--live-control` line protocol is the boundary used by the Python session manager. It accepts `snapshot`, `advance`, `closure <edge-id> <0|1>`, `outage <vehicle-id>`, `finish`, and `quit`.

Interventions are validated against the loaded C++ scenario and scheduled at the current simulation timestamp. Each accepted command emits an `OperatorIntervention` event before the corresponding native closure/outage event. The session log records simulation time, sequence, command, target ID and scenario name. Invalid target IDs are rejected by the simulator. Replaying a recorded action list resets the run, advances to each recorded event boundary, reapplies inputs in order, and finishes through the same native event queue.

## Unreal live mirror

Use the dashboard's **Launch Unreal mirror** control or pass `-RampLabLiveStateFile=<path-to-live-state.json>` alongside the scenario argument. The C++ session manager atomically refreshes the JSON state file; the Unreal subsystem polls it at 10 Hz and applies aircraft, vehicle, road, task, and event state to its existing presentation snapshot. In live-file mode the subsystem does not advance its local simulation. This is a read-only presentation feed, not a second authority or a physical control link. The polling interval bounds visual freshness to roughly 100 ms plus frame time; event history is included so transient operator and road events are retained between polls. Launching through the dashboard also requests a KAUO overview screenshot and records a synchronization line in the active run folder; the evidence bundler copies and hashes them as `evidence/interactive/unreal-live.png` and `evidence/interactive/unreal-live.log`. The demo runner captures after the 15-second closure while the same native session is paused at that event boundary.

## Validation and limits

Build the C++ project and run its CTest suite, then run the explicit Python suite covering Goal 24A ingestion, Goal 27 generation, Goal 19 analysis, Goal 20 dashboard/API, Goal 22 evidence, and Goal 28 live-session/replay behavior:

```powershell
ctest --test-dir build-goal28 -C Release --output-on-failure
$env:PYTHONPATH = 'tools/experiment_analysis'
python -m unittest tools.airport_data_ingestion.test_ingestion tools.airport_scenario_generation.test_kauo_goal27 tools.experiment_analysis.test_analyze tools.ops_dashboard.test_dashboard tools.ops_dashboard.test_real_bundle tools.ops_dashboard.test_live_session tools.evidence_bundle.test_bundle -v
```

The live operator interface is a local simulation control surface. It has no connection to airport systems, live traffic, or physical equipment. The state file and HTTP service are intended for local demonstration; the 10 Hz Unreal file feed is not a network protocol. KAUO geography and runway facts retain their source-backed status from Goal 27; apron geometry and operational details remain approximate or assumed.
